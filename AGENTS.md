# AGENTS.md

## Правила работы для агентов

1. **Соблюдай Conventional Commits** (например, `feat(files): ...`, `fix(tasks): ...`, `chore(tasks): ...`).
2. **Не добавляй** в коммиты подписи `Co-Authored-By`, `Signed-off-by` и другие атрибуции.
3. **Смена EOL в рабочем дереве** уже не должна появляться — файлы нормализованы через `.gitattributes` (`* text=auto`). Если `git status` вдруг показывает массовые «фантомные» изменения — запусти `git add --renormalize .`.
4. Проект использует **yarn** (не npm), Node 22, PostgreSQL.
5. **Стиль общения** Будь живым. Разговаривай как Джейсон Стэтхем, но без мата
6. **Именование веток** Если работаем с конкретным сервисом, ветки создаём с префиксом этого сервиса по принципу `<service>/<branch>` (например, `files-service/files-exception-filter`). Корневой `main` используется только для merge сервисов.

## Правила ветвления микросервисов

### Структура веток

Каждый микросервис развивается в собственной ветке с базовой веткой вида:

```text
service-<microservice>/main
```

Рабочие изменения создаются в дочерней ветке:

```text
service-<microservice>/<feature-or-fix>
```

Например:

```text
service-files/main
service-files/upload-streaming

service-tasks/main
service-tasks/filter-swagger
```

### Ограничение области изменений

- Ветка сервиса должна содержать только изменения этого микросервиса.
- Изменения другого сервиса оформляются в отдельной ветке.
- Общие изменения корня репозитория выносятся в отдельный согласованный коммит.
- Временные файлы, изображения, `node_modules` и локальные артефакты в коммиты не добавляются.
- Изменения не должны выходить за рамки назначения текущей ветки.
- Изменения, которые не касаются текущей ветки, но нужны, должны быть вынесены на обсуждение. Их либо сделать либо занести в TASKS.md, либо не делать

### Слияние

1. Изменения коммитятся в дочерней ветке сервиса.
2. После проверки дочерняя ветка вливается в `service-<microservice>/main`.
3. Слияние в корневую `main` выполняется только после отдельного подтверждения.

## Коммиты

- Коммить изменения согласно конвенции коммитов.
- Не сваливай всё в один огромный коммит. Коммиты должны быть логически распределены.
- При коммитах учитывай не только свои изменения, но если заметил, что есть ещё изменения - возьми их в учёт тоже.
